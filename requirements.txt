# The upper bound is load-bearing, and its VALUE was measured rather than copied.
#
# WHY A BOUND: on 2026-08-20 the sibling naukri server declared `mcp[cli]>=1.25.0`
# unbounded. `mcp 2.0.0` shipped, relocating mcp/server/fastmcp to
# mcp/server/mcpserver, and a clean resolve killed all 55 of its test modules at
# collection ("5 deselected, 55 errors", zero tests run) while every LOCAL naukri
# run stayed green on a venv holding mcp 1.26.0 from before 2.0.0 existed. An
# unbounded `>=` on a framework package is a time bomb lit by someone else's
# release, and a local venv -- a cache of a past resolve -- cannot see it.
#
# THIS SERVER WAS NOT AFFECTED BY THAT PARTICULAR MOVE, and that was verified,
# not assumed. It depends on the standalone `fastmcp` project, not `mcp[cli]`,
# and it imports `fastmcp` directly. Measured 2026-08-20 in a throwaway venv:
# after `import instahyre_server.server`, sys.modules held mcp.server.auth,
# mcp.server.experimental and mcp.server.models but NOT mcp.server.fastmcp --
# the relocated module is not in this server's import graph at all. fastmcp
# additionally caps its own dependency at `mcp<2.0,>=1.24.0`, so mcp 1.29.0 is
# what a clean resolve installs here and mcp 2.x cannot arrive by accident.
#
# WHY <4 AND NOT <3: a clean resolve today picks fastmcp 3.4.7 and the suite
# gives "242 passed in 5.11s" on it. Capping <3 would pin a working server to an
# older major for no reason anyone could point at -- the cargo-cult version of
# naukri's fix. The bound goes at the next UNKNOWN major instead: fastmcp 4.x is
# code nobody has run this against, and fastmcp 2.0 was itself a rewrite of the
# library that became mcp.server.fastmcp, so its majors have a track record of
# moving things. Raising this to <5 is a decision to go test on 4.x first.
# tests/test_requirements_pins.py fails if this cap disappears or narrows.
fastmcp>=2.0,<4

# jobcore -- the shared scoring engine (skill taxonomy, fit score, the policy
# object that `jobhunt.json` configures). Pure stdlib, no dependencies, shared
# with the naukri and uplers servers so a fit score means the same thing on all
# three. It is REQUIRED: instahyre_server/scoring.py imports it at module scope.
#
# It used to be optional, with a small local fallback scorer behind a
# `sys.path` insert at ../jobcore/src. Both are gone. The fallback did no skill
# aliasing at all -- "Node.js" on a job never matched "nodejs" on the profile --
# so it produced systematically lower numbers under the same `fit_score` key,
# and it could not read the shared config, which made it a second and
# unconfigurable engine the moment the weights became configurable. A missing
# jobcore is now a loud ImportError naming the fix.
#
# NOT A REQUIREMENT LINE HERE, and that is deliberate: a `jobcore @ git+...` in
# THIS file would silently uninstall a local `pip install -e ../jobcore`
# (measured 2026-08-20 -- pip prints "Attempting uninstall" and the "Editable
# project location" line disappears, with no "already satisfied" line to warn
# you). tests/test_requirements_pins.py holds that in place.
#
# INSTALL IT ONE OF THESE TWO WAYS:
#     pip install -e ../jobcore            # you have the sibling checkout
#     pip install -r requirements-ci.txt   # you do not: pinned, from git
# `ModuleNotFoundError: jobcore` means neither line was run.

# CI-only requirements. Use requirements.txt for local development.
#
# WHY THIS FILE EXISTS, measured rather than assumed:
# putting the jobcore git URL in requirements.txt CLOBBERS a local editable
# install. Verified on a clean venv 2026-08-20 in the sibling naukri repo --
# after `pip install -e ../jobcore`, running `pip install -r <file with the git
# URL>` printed "Attempting uninstall: jobcore / Successfully uninstalled", the
# "Editable project location" line disappeared from `pip show`, and the
# __editable__ shim was replaced by a real jobcore/ directory. Reproduced twice.
# pip prints no "Requirement already satisfied" line for a direct-URL
# requirement, so the clobber is silent unless you go looking.
#
# Local iteration on jobcore matters more than CI convenience, so CI is the side
# that installs from git and requirements.txt stays editable-friendly. Same
# arrangement as ../naukri/requirements-ci.txt.
#
# THIS FILE IS ALSO THE SIBLING-FREE RECIPE. A fresh clone with no ../jobcore
# beside it -- a CI runner, a new machine, scripts/clean_install_check.py --
# installs from here. jobcore is REQUIRED: instahyre_server/scoring.py imports
# it at module scope and there is deliberately no local fallback scorer (see the
# comment block at the top of that file for why the old one was deleted).
#
# LOCAL DEVELOPERS WITH THE SIBLING: do not use this file. See requirements.txt.

-r requirements.txt

# Pinned to an exact commit, not @master. This repo's tests assert specific
# policy behaviour -- tests/test_scoring_policy.py needs the `policy=` seam on
# the flat compute_fit_score API and the Tier-C load refusal, both added in
# jobcore 0.2.0 -- so a moving branch would let a commit in another repo turn
# this repo's CI red with no change here.
# Bumping this line is the visible, reviewable way to adopt a jobcore change.
#
# BUMPED 2026-08-21 to 16ae934, which renamed the result stamp from
# `policy_hash` to `scoring_hash` and gave `Loaded` a `scoring_hash` property.
# This repo's scoring.py and policy.py now read both, so the pin and the source
# have to move together: the OLD pin against the NEW source fails
# tests/test_scoring_policy.py with `KeyError: 'policy_hash'`, and the NEW pin
# against the OLD source would fail the same way in reverse. That coupling is
# exactly what the sibling naukri repo got wrong today -- it shipped a
# `from jobcore.policy import ...` while pinned to the commit before that module
# existed, and CI was red for three pushes.
#
# BUMPED 2026-08-22 to d1720c3, and this one is worth reading because the
# paragraph above did not prevent it. A commit in THIS repo added
# `instahyre_server/buildinfo.py` (imports `jobcore.buildinfo`) and
# `instahyre_server/paths.py` (imports `jobcore.paths`) and left this line on
# 16ae934 -- a commit whose `src/jobcore/` contains seven files and NEITHER of
# those modules. Every local run stayed green, because a local venv installs
# jobcore EDITABLE from ../jobcore and therefore always has whatever is newest
# on disk; CI installs from this pin and dies at COLLECTION with
# `ModuleNotFoundError: No module named 'jobcore.buildinfo'`. That asymmetry is
# the whole trap: the local suite cannot fail this way, so nothing on a
# developer box will ever tell you the pin is stale. The follow-up commit needs
# 0f557eb specifically anyway -- `Loaded.report(display=...)`,
# `Loaded.status_for`, `Loaded.known_paths` and `jobcore.paths.relativise_known`
# all arrived there. The pin is d1720c3 rather than 0f557eb because 0f557eb's
# own CI was red; pinning a red commit is how a green CI here stops meaning
# anything. d1720c3 is jobcore master, CI green, and 0f557eb is its ancestor.
#
# This was not a prediction. CI on that commit was RED on Python 3.10 and 3.11,
# every collection, with:
#     ImportError: cannot import name 'paths' from 'jobcore'
#     ImportError: cannot import name 'buildinfo' from 'jobcore'
# Note the SHAPE. This repo writes `from jobcore import buildinfo`, so a stale
# pin reads as `ImportError: cannot import name`; the sibling naukri repo writes
# `import jobcore.paths` and the identical root cause reads as
# `ModuleNotFoundError`. Two messages, one bug -- worth knowing before deciding
# you are looking at two.
#
# BUMPED AGAIN 2026-08-22 to 998baf1 (third bump in one day). jobcore now
# reports a pip-installed dependency by VERSION where there is no work tree to
# read a commit from, via `buildinfo.self_stamp()`, which instahyre_server/
# buildinfo.py calls. d1720c3 has the buildinfo MODULE but not that FUNCTION,
# so the stale-pin failure that time was:
#     AttributeError: module 'jobcore.buildinfo' has no attribute 'self_stamp'
#
# THE RULE, learned the same way three times: a `from jobcore...` import and a
# pin bump are ONE change, never two. Local green says nothing about it -- the
# local venv is editable from ../jobcore and always has the newest code, so the
# local suite CANNOT fail this way.
#
# THIS IS NOW CHECKED MECHANICALLY. tests/test_jobcore_pin.py reads this pin,
# reads jobcore's source AT THAT COMMIT out of the ../jobcore clone (offline,
# no fetch, never imported), and asserts every jobcore MODULE and every NAME
# and ATTRIBUTE this repo uses exists there. It caught this very bump before
# it was pushed. It skips cleanly when the sibling clone is absent, so it is a
# local pre-push guard, not a CI check -- which is the right place for it,
# because CI is the round trip it exists to save.
#
# BUMPED AGAIN 2026-08-22 to 6acc7e6 (fourth bump in one day), and this one is
# a different KIND of bump from the three above it. Those adopted new jobcore
# NAMES and would have broken the import if forgotten. This one adopts changed
# BEHAVIOUR behind names that already existed: 6acc7e6 teaches
# jobcore.paths.relativise_known that a path has a second spelling, because
# OSError.__str__ renders its filename through repr() and doubles the
# separators on Windows.
#
# WHAT THAT MEANS FOR THE MECHANICAL CHECK, and it is worth stating because the
# check reads as more protective than it is. tests/test_jobcore_pin.py verifies
# that every jobcore module, name and attribute this repo uses EXISTS at the
# pinned commit. It says nothing about how any of them BEHAVES. Measured, both
# commits, same scanner:
#
#     998baf1   unsatisfied: NOTHING -- passes
#     6acc7e6   unsatisfied: NOTHING -- passes
#
# So this bump is invisible to it, by construction. Names existing is not names
# behaving, and no signature changed here. A behaviour bump has to be adopted
# deliberately, by a human reading the upstream commit -- there is no check that
# will remind you.
#
# WHY BUMP AT ALL, since instahyre does not need it: instahyre_server/paths.py
# passes BOTH spellings of every needle to relativise_known itself, so the
# repr-separator leak is already closed here at 998baf1. The reason is fleet
# consistency -- naukri is on 6acc7e6, and one jobcore across the family for a
# stated reason beats two by accident.
#
# DO NOT DELETE instahyre_server/paths.relativise_prose AS REDUNDANT once this
# pin is in. It looks redundant now that jobcore handles the second spelling
# upstream, and it is not: unlike the sibling servers this repo has NO
# server-wide boundary scrubber over tool results, so relativise_prose is the
# only boundary between a composed error message and the wire. It stays
# load-bearing regardless of what jobcore does.
#
# THE CHECK, before pushing anything that adds a `from jobcore...` import:
#     git -C ../jobcore ls-tree --name-only <this pin> src/jobcore/
# If the module you just imported is not in that listing, CI is already red --
# and note that a listing CANNOT show you a missing attribute, and neither a
# listing nor the automated check can show you a changed behaviour.
